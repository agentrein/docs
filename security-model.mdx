AgentRein enforces a strict security boundary between automated agent clients and human operators.

---

## 1. Authentication Scopes

AgentRein separates authentication into two distinct categories:

### Agent API Keys (`ar_live_...` / `ar_test_...`)

Agent API keys authenticate SDK client instances. Upon initialization, the SDK exchanges the API key for a short-lived Bearer token via `POST /auth/token`.

API keys are restricted to an allow-list of SDK operational endpoints:
- `POST /sessions` — Create session
- `GET /sessions/:id` — Read session state
- `PATCH /sessions/:id` — Complete session
- `POST /sessions/:id/rollback` — Trigger session rollback
- `POST /sessions/:id/actions/precapture` — Capture pre-mutation state
- `POST /sessions/:id/actions` — Log action
- `PATCH /sessions/:id/actions/:actionId` — Update action status
- `GET /approvals/:id` — Poll approval status
- `GET /registry` — Fetch connector registry capabilities
- `GET /settings/credentials/validate` — Validate connector credentials

<Warning>
  API key tokens cannot call administrative or operator routes. Attempting to access operator routes (such as policy creation or approval resolution) with an API key returns HTTP `403` with problem type `operator-required`.
</Warning>

### Dashboard / Operator Tokens

Human operators log in via the dashboard to obtain operator session tokens. Operator tokens have full access to management features:
- Managing policies (`/policies`)
- Resolving approval requests (`/approvals/:id/approve`, `/approvals/:id/reject`)
- Creating or revoking API keys (`/api-keys`)
- Viewing audit logs (`/audit-logs`), org metrics (`/metrics`), and intent drift logs (`/sessions/intent`)

## 2. Server Enforcement & Boundaries

<Warning>
  **SDK Cooperation Guarantee**: Server-side policy results and safety tracking are recorded and enforced as far as the SDK cooperates. An agent that bypasses the AgentRein SDK and invokes external APIs directly is not blocked by the server.
</Warning>

- **Pre-execution Blocking**: Pre-execution blocking occurs when actions are explicitly declared in `wrap()` using `requiresApproval`. The SDK pauses local execution before calling the external provider while polling for approval.
- **After-the-Fact Policy Enforcement**: Standard SDK calls evaluate policy rules when logged to `POST /sessions/:id/actions`. If a policy specifies `BLOCK`, the backend transitions the action to `FAILED` and returns HTTP `403`. If a policy specifies `REQUIRE_APPROVAL`, the backend creates an after-execution approval request; if rejected, single-action rollback is triggered.
- **No Pre-Execution Authorize Endpoint**: AgentRein does not expose a pre-execution authorization endpoint.

---

## 3. Resilience & Failure Modes

When initializing the client, the `failureMode` option controls SDK behavior when communicating with the AgentRein backend or encountering server errors:

- **`failureMode: 'open'` (Default)**: If action creation or logging fails—including HTTP `403` server denials (such as `policy-blocked` or plan gate requirements) or network outages—the SDK logs a warning (`console.warn` in Node.js / `logging.warning` in Python) and permits local execution of the tool call to proceed without backend safety tracking or approval gating.
- **`failureMode: 'closed'`**: If backend errors, server denials, or network failures occur, the SDK re-throws the underlying HTTP status error or raises `AgentReinUnavailableError` and halts agent execution immediately to prevent unmonitored or unapproved production actions.

<Warning>
  **Open Mode Swallows Server Denials**: In `failureMode: 'open'` (the default setting), server denials such as HTTP `403 Blocked by Policy` (`policy-blocked`) or `Upgrade Required` (`plan-required`) are swallowed as warnings, allowing local SDK tool execution to proceed. Use `failureMode: 'closed'` in high-security environments where server denials must strictly block execution.
</Warning>
